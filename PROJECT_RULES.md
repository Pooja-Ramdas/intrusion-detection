# PROJECT_RULES.md
# Distributed Multiclass Intrusion Detection and Traffic Profiling on Flow-Level and Packet-Level Data

## Problem Statement

Modern network security operations centres must process and classify tens of millions of flow
records and packet captures per day. The CIC-IDS2017 dataset provides labelled flow-level
features (generated by CICFlowMeter) and raw packet captures across five attack-day scenarios,
while UNSW-NB15 offers a complementary flow set for cross-dataset validation. Both datasets
exhibit severe class imbalance — benign traffic outnumbers individual attack classes by orders of
magnitude — making naive single-machine approaches impractical: they cannot fit the data in RAM,
and training times become prohibitive. A distributed architecture is required both to partition
the data across HDFS blocks and to exploit data-parallel model training via Spark MLlib.

The project couples a distributed storage and processing tier (HDFS + PySpark) with a
document-oriented query layer (MongoDB) that models each network flow together with its
associated packet records as a nested document. This design supports interactive analyst queries
— e.g. "show all HTTP-exfiltration flows with payload entropy > 0.9 during Tuesday's attack
window" — without a full table scan. Class imbalance is addressed via stratified sampling and
MLlib's `weightCol` / oversampling mechanisms. Results, traffic profiles, and Spark scalability
measurements are surfaced through a containerised Streamlit dashboard, satisfying the Docker
grading rubric by ensuring every process runs inside a container.

## Objectives

1. **Ingest & distribute** flow-level and packet-level CIC-IDS2017 data (UNSW-NB15 for
   validation) on an HDFS cluster and profile it with PySpark (row counts, schema, class
   distribution).
2. **Model** flows and their packets as nested MongoDB documents and evaluate indexed and
   aggregation queries for attack investigation (latency benchmarks saved to `artifacts/`).
3. **Engineer** flow-level features at scale, including header fields and payload-byte
   statistics (mean, std, entropy of payload bytes per flow).
4. **Train and compare** distributed MLlib classifiers (Logistic Regression, Random Forest,
   GBT) for binary and multiclass detection while handling class imbalance via stratified
   weights; report F1, precision, recall, and confusion matrices.
5. **Containerise** the entire pipeline with Docker Compose and present detection results,
   traffic profiles, and Spark scalability measurements through a Streamlit dashboard.

## Stack

| Layer | Technology |
|---|---|
| Distributed storage | Apache Hadoop HDFS 3.2 (bde2020 Docker image) |
| Distributed compute | Apache Spark 3.5 standalone + PySpark + MLlib |
| Document store | MongoDB 7 (PyMongo + Mongo Spark Connector) |
| Container runtime | Docker Desktop (WSL2 backend) + Docker Compose |
| Dashboard | Streamlit + Plotly |
| Dataset access | `huggingface_hub`, `nids-datasets` |
| Data wrangling | pandas, pyarrow |

## Resource Limits

| Resource | Limit |
|---|---|
| Host free disk (C:) | ~10 GB — keep staging data deleted after ingest |
| Docker VHDX (D:) | 45 GB available |
| Raw dataset working set | ≤ 600 MB total across all three datasets |
| WSL2 memory cap | 8 GB (set in `.wslconfig`) |
| Spark worker memory | 1.5 GB × 2 (configurable via `.env`) |

## Operational Rules

- **Be terse.** No lengthy explanations in code comments; self-documenting names.
- **Run everything via Docker.** No Python, Java, or Hadoop on the host.
- **After each phase**, write an evidence file to `docs/evidence/phaseN.md` containing exact
  commands run and real (copy-pasted) outputs. Never fabricate results.
- **If something fails, say so.** Record the error and the fix in the evidence file.
- **Never download full datasets.** Respect the 600 MB working-set cap; trim immediately.
- **Preserve named volumes** (`mongo_data`, `namenode_data`, `datanode*_data`). The cleanup
  script (`scripts/cleanup.ps1`) deliberately does NOT run `docker system prune --volumes`.
